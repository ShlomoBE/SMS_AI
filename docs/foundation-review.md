# Foundation review

Review date: 2026-11-06. Scope: foundation and configuration, against interface contract v0.1; active CPU implementation and CPU test files excluded. This is a point-in-time review, not an integration sign-off.

## Prioritized findings

1. **High — target/runtime support expires imminently.** Both project files target `net8.0` (`src/Sms.Core/Sms.Core.csproj:4`, `tests/Sms.Core.Tests/Sms.Core.Tests.csproj:4`). Microsoft lists .NET 8 and 9 support ending **2026-11-10**, four days after this review; .NET 10 LTS is supported until 2028-11-14. `README.md:7` states the target but not this risk. Ask the owner to approve a supported LTS target/SDK and migration schedule; do not silently retarget. Validate package compatibility and run restore/build/tests on each supported platform. Source: [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core).

2. **High — ROM/BIOS protection only covers a directory name, not the assets.** `.gitignore:5-7` ignores directories named `Roms` and two save extensions, but a supplied `.sms` or BIOS file placed elsewhere, a differently named directory, an archive, or other save formats is not covered. Ignore rules do not protect already tracked files or prevent forced additions. The current workspace is not a Git repository, so tracked/index status and actual `git check-ignore` behavior here were not verified. Agree an asset policy, consider extension/path guards with explicit reviewed exceptions for licensed fixtures, and validate with synthetic names and a staged-content check before any initial commit. Never inspect or add the supplied ROM contents for this check.

3. **Medium — SDK selection and prerequisites are not reproducible.** `README.md:7` gives a command, but does not specify required SDK and .NET 8 runtime, restore/network prerequisites, or roll-forward policy; there is no `global.json`. Here `dotnet --info` reports SDKs 6.0.428, 8.0.427 and 9.0.320, selecting 9.0.320, with .NET 8 runtime 8.0.33 installed. A newer SDK can target net8.0, but does not by itself guarantee the target runtime is installed for test execution. Choose and document a supported SDK/runtime and roll-forward policy, optionally pin SDK via `global.json` after approval, then exercise clean-machine restore/test in CI. `docs/architecture.md:7` also incorrectly leaves the test framework and target unselected despite the xUnit/net8.0 project configuration.

4. **Medium — README gives contradictory project and agent setup.** `README.md:5-9` describes an implemented C# project and OpenCode agents; lines 12-19 instead direct a new Codex-only bootstrap, and lines 35 and 38 claim no language has been chosen and no emulator implementation exists. The role list omits OpenCode's `audio_fm` agent. Update the document for the actual repository, separate Codex and OpenCode instructions, and avoid exact instruction-coverage claims while CPU work is ongoing. Similarly `docs/architecture.md:48-64` describes conceptual pre-language paths although `src/Sms.Core` exists; mark them as proposals or update ownership to actual approved paths.

5. **Medium — Codex concurrency/model statements do not configure OpenCode.** `README.md:32-37` and `.codex/config.toml:1-5` concern Codex; they do not establish a four-agent OpenCode concurrency cap. OpenCode definitions explicitly bind `model: provider/model#variant` (for example `.opencode/agents/z80_cpu.md:4`), so they do not inherit the parent model by default. The syntax itself is documented by [OpenCode V2 agents](https://opencode.ai/v2/docs/agents); availability, subscription access, effective merged config, and actual Codex config compatibility were not tested. Clarify harness-specific behavior and verify each runtime's effective settings instead of promising a shared cap or universal inheritance.

6. **Medium — foundation gate is not evidenced by independent automation.** `docs/roadmap.md:8` requires reproducible build/tests, harness, conventions and CI design, but no CI configuration or independent foundation/asset-policy tests were found. Presence of compiled output is not evidence of a current passing build. Add clean restore/build/test jobs after choosing SDK policy, plus synthetic ignore-policy and boundary/contract tests as interfaces are implemented; report incomplete gate items explicitly.

7. **Low — reference redistribution wording conflicts with local files.** `docs/hardware-assumptions.md:35` says the project does not redistribute the copied document while `IDocs/General.txt` is present in this workspace. Local presence does not establish publication, but a future repository/distribution could inadvertently include it and other `IDocs` files. Review each file's license and intended distribution status before publication; update wording and ignore/replace restricted references as appropriate. The CPU QA plan itself says not to redistribute the Zilog manual (`docs/z80-test-plan.md:7`).
